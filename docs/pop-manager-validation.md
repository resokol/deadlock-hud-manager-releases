# Pop Manager 2.0 · архитектура и проверка

## Распределение ответственности

1. **Комната VDO.Ninja** работает в одной встроенной сессии Qt WebEngine. Локальный мост получает директорию и признаки видео через IFrame API. Для авторизации открывается та же сессия. Участник с известным Stream ID может присутствовать с выключенной камерой. Потеря связи со всей комнатой приостанавливает команды отключения камер. При оценке видео менеджеру может потребоваться низкобитрейтный предпросмотр. Настоящие браузерные входы vMix остаются потребителями эфирных потоков. [Обработчик VDO.Ninja](https://github.com/steveseguin/vdo.ninja/blob/develop/main.js)
2. **Предматчевая подготовка** сравнивает имена комнаты с сохранёнными назначениями GUID, проверяет весь пул и обновляет изменившиеся входы. Раньше требовалась отдельная вкладка браузера, повторное нажатие «Подготовить» и отдельная привязка копий после распределения. Теперь инвентаризация запускается от события комнаты; редактор пула нужен при первичной настройке и спорных соответствиях.
3. **Синхронизация с матчем** получает подтверждённый порядок портретов, готовит 12 пар и выполняет одну последовательность команд Web Controller. Отдельно хранит закреплённую раскладку и новый порядок в предпросмотре. Для физической перестановки использует существующие GUID, проверяет следующий каталог и ведёт журнал восстановления. Скрытые геометрические параметры сохраняет сам пресет vMix.
4. **Монитор доступности** обслуживает оригинал и нативную копию. С подтверждённой непрозрачностью обоих входов применяет SetAlpha и восстанавливает предыдущее значение каждого. При недостатке данных один оригинал временно получает прозрачную страницу. Появление нового URL может потребовать повторного соединения. Навигацию копии монитор не использует.
5. **Маршрутизация** остаётся в vMix. Постоянная команда кнопки по физическому номеру и переменная имени оригинала по номеру дают независимый Live и Replay. Опциональное управление менеджера проверяет текущий Mix перед выбором. Процесс менеджера не участвует в прямой команде Companion.

## Возможности vMix

| Операция | Действие и проверка |
|---|---|
| Назначить индивидуальный URL | BrowserNavigate по GUID браузера. Каталог и ответ управляющего запроса подтверждают назначение; появление кадра зависит от WebRTC. |
| Получить нативную копию | CreateVirtualInput по GUID оригинала в явной настройке пула. После команды проверяется появление нового GUID. При неопределённом ответе требуется повторное чтение, а не повторное создание. |
| Переименовать и переместить | SetInputName и MoveInput, сверка номеров, названий и доступных родительских ссылок в свежем XML. У vMix нет документированной атомарной сортировки двух банков. |
| Полный кадр копии | SetCrop, SetZoom, SetPanX и SetPanY. Поворот, произвольное отражение и переопределённые пропорции проверяют вручную. |
| Скрыть вход | SetAlpha принимает 0–255. Наличие этой команды не гарантирует, что XML возвращает прежнее значение. Пустая страница общего браузера служит альтернативой для копии и оригинала. |
| Передать альфа-канал | Составляющая alpha внутри vMix и передача через физический External 2 — две разные проверки. Проверьте режим ключа и оборудования на приёмнике. |

[API и команды vMix](https://www.vmix.com/help29/ShortcutFunctionReference.html) · [XML Web Controller](https://www.vmix.com/help29/DeveloperAPI.html) · [Fill и Key](https://www.vmix.com/help29/KeyFill.html)

## Воспроизводимые проверки

Тестовый контроллер обслуживает настоящий HTTP на loopback и отдаёт XML пресета. В нём 12 оригиналов, 12 независимых GUID виртуальных копий и один посторонний вход. Модель меняет физические номера и возвращает состояние Program по GUID. Тесты не подключаются к действующему эфиру.

| Проверка | Измеренный результат на стенде |
|---|---|
| 1 200 смен игрового порядка | 17 164 перемещения за 138 с. Медиана синхронизации 100 мс, максимум 266 мс. В каждом каталоге тот же пул и тот же посторонний вход. Во время сортировок — 0 навигаций браузера, 0 переключений Program. RSS тестового процесса после прогрева и в конце — 58 612 и 59 220 КиБ. |
| Скрытие и возвращение 12 камер | 24 изменения состояния, 48 SetAlpha. На loopback от передачи подтверждённого события в монитор до приёма второй команды пары — медиана 22 мс, максимум 35 мс. При отдельном опыте без события резервный опрос с интервалом 2 с отправил обе команды за 1,91 с. Эти измерения исключают подтверждение события у VDO.Ninja и появление первого кадра WebRTC. |
| Реальный обработчик модуля StudioCoast vMix 5.0.5 | 30 раскладок, 360 нажатий, 720 проверок подписей. Для позиции 7 модуль отправлял `FUNCTION ActiveInput input=19&mix=1` (Mix 2 интерфейса). Команды перехватывал тестовый TCP-приёмник. |
| Изменения и восстановление | Интеграционные сценарии покрывают включение/исчезновение отдельной камеры при присутствующем госте, неоднозначное состояние комнаты, позднее подключение, проверку происхождения виртуальной копии, перезапуск, сбои команды и изменения пресета оператором. |
| Пользовательские настройки и кадровая геометрия | Проверяются отдельные прежние значения alpha, нейтральные параметры виртуального входа и сохранение доступной геометрии оригинала. Восстановление полномасштабного кадра, реальное состояние WebRTC и тракт External 2 требуют проверки на приёмнике. |

Для повторения запустите в тестовом окружении `python -m pytest -q`. Нагрузочный прогон задаётся через переменную окружения `POP_TEST_MATCHES=1200` и тест `tests/test_camera_tournament_load.py`. Для проверки Companion соберите модуль StudioCoast vMix тега `v5.0.5` и передайте каталог `dist` в `node tests/integration/companion-vmix-pairs.mjs <путь-к-dist>`. Для проверки эфирных ограничений сохраните пресет и пройдите [две точки проверки прозрачности](pop-manager-2.md).
